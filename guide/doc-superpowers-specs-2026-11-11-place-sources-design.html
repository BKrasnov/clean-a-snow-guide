Мир плейсов в репозитории

Карточка 670e36, мир C из разбора ca1233 (docs/architecture/place-world.html), №16 сводки dc68a4. 11.11.2026.

Задача

Мир (остров, долина, Terrain, интерфейс CleanSnowUI, CleanSnowAssets, ассеты сада, звуки, материалы, свет) живёт только в файлах place/*.rbxl, которых нет в git. Три файла — NaLovi.rbxl (оба мира, 42 МБ, из них почти всё — 628 тыс. объектов резервных копий в ServerStorage), NaLovi-Lobby.rbxl и NaLovi-Match.rbxl — правятся по отдельности и расходятся. Нужен один источник правды в репозитории, из которого собираются все три файла.

Игрок ничего не заметит.

Решения владельца

Решение владельца 11.11.2026:

  • мир правится в Studio в собранном файле, потом команда выгрузки кладёт правку в репозиторий; сборка не перезаписывает файл с невыгруженной правкой мира;
  • place/NaLovi.rbxl (файл для Play) тоже собирается из репозитория: долина и остров, без резервных копий; старый файл уходит в place/backup/;
  • резервные копии из ServerStorage в репозиторий не брать; старый файл с ними остаётся на диске в place/backup/.

Почему не два проекта Rojo

Карточка предлагала два проекта Rojo. Разбор плейсов показал, что содержимое мира перемешано с кодом: модули сада (CleanSnowGardenAssets/PlantGenerationModules) держат внутри модели, детали и анимации, в папке CleanSnow рядом с модулями лежат Remotes и Art, в CleanSnowUI — скрипт. Чтобы Rojo собрал такое, пришлось бы разрезать src/ на сотни .rbxm и мета-файлов. Terrain через проект Rojo не везётся.

Поэтому мир собирает Lune, как уже сейчас в tools/places/build.mjs, а код по-прежнему кладёт Rojo из общего default.project.json. Проект Rojo для кода остаётся один на все места.

Как хранится мир

models/ — содержимое мест по слоям:

models/
  places.json            какие слои у какого места
  shared/<Сервис>/<Имя>.rbxm   то, что одинаково у лобби и долины
  lobby/services.rbxl    свойства сервисов лобби (скелет без детей)
  lobby/<Сервис>/<Имя>.rbxm
  match/services.rbxl
  match/<Сервис>/<Имя>.rbxm
  • Часть — все дети сервиса с одним именем (например, 20 Low Poly Mountain в одном файле). Файл не меняется, пока не правят эту часть, поэтому git растёт только на правленое. Terrain — обычная часть Workspace/Terrain.rbxm.
  • Скелет services.rbxl — место без детей сервисов: свойства Workspace, Lighting, StarterPlayer и других.
  • Код не хранится в частях. В сервисах, которые заполняет Rojo (ServerScriptService, ReplicatedStorage, StarterPlayer, StarterGui, ServerStorage), выгрузка убирает скрипты и папки, в которых только код. Скрипт, у которого внутри есть содержимое (модель, деталь, анимация), остаётся с пустым текстом: его текст впишет сборка из src/. Пустые папки остаются.
  • StudioRole на Bootstrap в части не попадает: роль ставит сборка по places.json.

places.json:

Место Файл StudioRole Слои (первый — свой) Добавки
Lobby place/NaLovi-Lobby.rbxl Lobby lobby, shared —
Match place/NaLovi-Match.rbxl Match match, shared —
Dev place/NaLovi.rbxl нет match, shared Workspace/LobbyArea из lobby

Часть места берётся из первого слоя, где она есть; добавки — из названного слоя. Dev — долина вместе с островом, как нынешний NaLovi.rbxl без резервных копий.

Старые снимки models/Workspace/*.rbxm и models/ServerStorage/BrrrMechanicsTemplate.rbxm устарели (их актуальные версии — в частях мест) и удаляются; они остаются в истории git.

Сборка

node tools/places/build.mjs [коммит] (по умолчанию origin/main) для каждого места:

  1. берёт models/ и src/ из выгрузки коммита (git archive), рабочая папка не участвует;
  2. Lune собирает основу: скелет, части по слоям, StudioRole;
  3. Rojo собирает код, Lune вписывает его в основу (bake, как сейчас);
  4. проверки как сейчас (каждый скрипт байт в байт с git, нет старого кода) плюс: мир собранного файла совпадает с миром коммита;
  5. защита правки: если в нынешнем файле места мир отличается от того, что записала прошлая сборка (build/places/build.json), значит, его правили в Studio и не выгрузили — файл не трогается, сборка просит выгрузить. --force перезаписывает. Старый файл в любом случае уходит в place/backup/.

--check только проверяет, что файлы несут код и мир коммита.

Выгрузка

node tools/places/export.mjs <Lobby|Match|Dev> [файл] — читает файл места (по умолчанию из places.json) и пишет его мир в рабочую папку models/:

  • изменённая часть пишется в тот слой, откуда место её берёт (правка общей части из лобби меняет её и для долины);
  • новая часть — в свой слой места (для Dev — match);
  • часть, которой в файле больше нет, удаляется из своего слоя;
  • скелет — в свой слой.

Выгрузка печатает, что записала и удалила, и ссылки между частями, которые не сохранятся (сейчас две: сохранения анимации KESTREL_07 в редакторе).

node tools/places/export.mjs share переносит в shared части, одинаковые у lobby и match. Нужна при первом переносе и если одну часть добавили в оба места.

Порядок работы: правка в Studio → сохранить файл → выгрузка → коммит и push → сборка.

Перенос

  1. Выгрузить Lobby из place/NaLovi-Lobby.rbxl и Match из place/NaLovi-Match.rbxl, затем share.
  2. Закоммитить models/.
  3. Собрать все три места. NaLovi.rbxl старый — с первого раза --force, старый файл уходит в place/backup/.
  4. Play в своём окне: Dev (окно чата), Lobby и Match (сценарии publish-lobby, publish-match).

Что не меняется

  • npm run play -- window и npm run test:game берут те же пути.
  • rojo serve для живой правки кода.
  • Публикация — по docs/publish-places.md, только владельцем.

Тесты

  • Место получает части своих слоёв: Dev — остров из lobby и Terrain долины, лобби — без частей долины.
  • Выгрузка: правка общей части уходит в shared, новая часть — в свой слой, исчезнувшая удаляется, неизменённая не пишется.
  • Имя части, недопустимое в Windows, кодируется; две части, отличающиеся только регистром, — понятная ошибка.
  • Защита правки: сборка отказывается, если мир файла отличается от записи прошлой сборки, и проходит, если совпадает.
  • Lune на маленьком месте: выгрузка убирает код, но оставляет модель внутри скрипта и пустую папку; сборка из частей и повторная выгрузка дают те же части.
